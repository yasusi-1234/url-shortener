# CLAUDE.md（frontend / React・TypeScript）

## 役割
このディレクトリは **画面（フロントエンド）**。backend の REST API を叩いて動作する。
UI の要件は、親フォルダの `url-shortener-design.md` 第7章を参照。

## 技術
- React + TypeScript
- ビルドツール: Vite（開発サーバーは例として 5173 番）
- パッケージ管理: npm（Gradle は使わない）

## 作るもの（レベル1）
- URL 入力フォーム＋短縮ボタン1つ。
- 送信で `POST /api/shorten` を呼び、返ってきた shortUrl を画面に表示する。
- 短縮URLのコピー用ボタン（任意）。
- 入力が空・不正な場合の簡単なエラー表示。

## コーディング規約
- TypeScript の型をきちんと付ける（API のレスポンス型を interface / type で定義する）。any を避ける。
- API を叩く処理は、画面コンポーネントに直書きせず、専用の関数/モジュールに分ける（責務の分離）。
- backend の URL（http://localhost:8080 等）は環境変数（.env の VITE_API_BASE 等）で持ち、直書きしない。

## backend との連携
- backend は別ポートで動くので、CORS は backend 側で許可される前提。
- API 仕様（リクエスト/レスポンスの形）は url-shortener-design.md 第6章に合わせる。

## コマンド
- `npm install`   … 依存インストール
- `npm run dev`   … 開発サーバー起動
- `npm run build` … 本番ビルド

## テスト
- frontend にも軽量なテストを導入する（Vitest 等）。
- ただし対象は API呼び出しやデータ整形などのロジック部分に絞る。グラフの見た目・描画結果は目視確認とし、UIの複雑なテストは今回は行わない。
- テストケース名（`describe`/`it`等）は「Given（前提）/ When（操作）/ Then（結果）」のガーキン形式で「何を検証しているか」を日本語で記述する。
- **実装完了報告の際は、この Given/When/Then を一覧にして人間に伝える。** テストコードを読まなくても、各テストが何を検証したかを報告文面だけで把握できるようにする（レビュー負荷の軽減が目的であり、テストケース名の書き方はそのための手段）。

## 報告のルール
報告の読み手は**コードを読まない監督者**であることを前提にする。

- 実装完了報告・テスト結果報告は、**冒頭に結論を置く**。✅/⚠️/❌ などの記号付きで「完了・全◯件成功」「◯件失敗（要対応）」のように、1〜2行で一目で成否が分かるサマリを書く。
- その下に、詳細（Given/When/Thenの一覧、影響範囲など）を続ける。「まず結論、次に詳細」の順にし、詳細を全部読まなくても成否が即座に分かるようにする。
- **テスト結果のGiven/When/Thenは、実装の関数名・メソッド名ではなく「要件・機能の言葉」で書く。** 例：「`getStats`を呼ぶ」ではなく「あるURLの統計を見ようとする」。テストコード内のテストケース名は実装寄りの書き方でよいが、報告のときは機能の言葉に翻訳する。
- **ファイル変更の報告では、技術的な「何を作ったか」より前に、「この変更でアプリとして何ができるようになったか（利用者視点）」を書く。** 例：「短縮URLごとに日別クリック数をグラフで見られるようになった」→ それを実現するための変更、の順で書く。
- **報告は「機能」という軸で構造化する。** コードを読まない監督者が"機能"単位で「できること」「テストの網羅性」を把握できるようにするため。
  - 「何ができるようになったか」はフラットな箇条書きにせず、`■機能名 → その機能でできること（複数可）`の形でグルーピングする。
    例：
    ```
    ■ クリック計測機能
    　→ アクセスを日時・端末・ブラウザ単位で記録できる
    　→ 記録に失敗しても転送は影響を受けない
    ```
  - テスト結果のGWTも、1つの大きな表にまとめず、`■◯◯機能のテスト`という見出しごとに機能単位の小さな表に分割する。
