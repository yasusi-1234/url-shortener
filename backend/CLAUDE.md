# CLAUDE.md（backend / Spring Boot・Java）

## 役割
このディレクトリは **API専用のバックエンド**。画面（Thymeleaf等のテンプレート）は持たない。JSONを返すことに専念する。
API仕様の詳細は、親フォルダの `url-shortener-design.md` 第6章を参照。

## 技術
- Java / Spring Boot
- DB: PostgreSQL
- ビルド: Gradle（build.gradle はこの backend 直下）

## アーキテクチャ（レイヤード）
- `controller/` … REST エンドポイント。リクエストを受けて Service を呼ぶだけ。ロジックを書かない
- `service/`    … ビジネスロジック（キー発行・衝突チェック・登録・検索）を集約
- `repository/` … DB アクセス（urls テーブル）
- `model/` または `entity/` … ドメインオブジェクト
- `dto/`        … API のリクエスト/レスポンス用。エンティティを直接APIに晒さない

## コーディング規約
- コンストラクタインジェクションを使う（フィールドインジェクションは使わない）
- 入力検証は Bean Validation（@Valid 等）を使う
- 例外は @ControllerAdvice で一元的にハンドリングする
- 層をまたぐ責務の混在を避ける（Controller にロジックを書かない、等）

## このアプリ固有のルール
- 短縮キーは a-z A-Z 0-9 の62文字からランダムに6文字生成し、DBに既存なら生成し直す（衝突チェック）。
- short_key には UNIQUE 制約を付け、DBレベルでも重複を防ぐ。
- 内部ID（id）は外部レスポンスに出さない。外部に見せるのは short_key のみ。
- 同一URLの再登録でも毎回新しいキーを発行する。
- 存在しない short_key へのアクセスは 404 を返す。
- フロント（別オリジン）から /api/** を叩けるよう CORS を設定する。


## テスト
- Service のロジックは単体テストを書く（特にキー生成・衝突時の再生成）
- Controller は @WebMvcTest 等でテストする

## コマンド
- `./gradlew bootRun` … 起動
- `./gradlew test`    … テスト
- `./gradlew build`   … ビルド

## レベル2実装における開発の進め方・レビュー負荷を減らすルール
（`url-shortener-design.md` 第10章「レベル2仕様：クリック履歴と可視化」の実装に適用する）

### 開発の流れ
- 各機能は「実装 → 単体テスト作成 → 自己チェック（抜け漏れ・設計との齟齬の確認）」の順で進める。
- テストが通ることを、目視レビューの代わりの品質担保とする。

### 人間に報告するもの・しないもの
- 自信を持って処理できたものは逐一報告しない（レビュー負荷を下げる）。
- ただし以下は必ず人間に報告し、判断を仰ぐ：
  - 実装の判断に迷った点、複数の選択肢があり決めきれない点
  - 要件が曖昧・不足していると感じた点（曖昧なまま進めず、先に確認する）
  - 「設計書のこの部分はこうした方が良いのでは」と感じた改善提案

### 安全のための停止ルール
- 既存のレベル1のコード（urls関連・短縮・リダイレクトの既存動作）を変更する必要が生じた場合は、自動で進めず必ず停止して、変更内容を報告してから進める。
- `clicks` へのINSERTを追加しても、リダイレクト自体が失敗しないようにする（計測の失敗が本来の転送機能を巻き込まないこと）。

### 最終報告
- 実装後、「何を追加し、既存のどこに影響したか」「テスト結果」を要約で報告する。

### テストの書き方
- 単体テストには `@DisplayName` を付け、「Given（前提）/ When（操作）/ Then（結果）」のガーキン形式で「何を検証しているか」を日本語で記述する。
- **実装完了報告の際は、この Given/When/Then を一覧にして人間に伝える。** テストコードを読まなくても、各テストが何を検証したかを報告文面だけで把握できるようにする（レビュー負荷の軽減が目的であり、`@DisplayName`はそのための手段）。

### フロントエンドのテスト
- フロントのテスト方針は `frontend/CLAUDE.md` を参照。

## 報告のルール
報告の読み手は**コードを読まない監督者**であることを前提にする。

- 実装完了報告・テスト結果報告は、**冒頭に結論を置く**。✅/⚠️/❌ などの記号付きで「完了・全◯件成功」「◯件失敗（要対応）」のように、1〜2行で一目で成否が分かるサマリを書く。
- その下に、詳細（Given/When/Thenの一覧、影響範囲など）を続ける。「まず結論、次に詳細」の順にし、詳細を全部読まなくても成否が即座に分かるようにする。
- **テスト結果のGiven/When/Thenは、実装の関数名・メソッド名ではなく「要件・機能の言葉」で書く。** 例：「`getStats`を呼ぶ」ではなく「あるURLの統計を見ようとする」。テストコード内の`@DisplayName`は実装寄りの書き方でよいが、報告のときは機能の言葉に翻訳する。
- **ファイル変更の報告では、技術的な「何を作ったか」より前に、「この変更でアプリとして何ができるようになったか（利用者視点）」を書く。** 例：「短縮URLごとに日別クリック数をグラフで見られるようになった」→ それを実現するための変更、の順で書く。
- **報告は「機能」という軸で構造化する。** コードを読まない監督者が"機能"単位で「できること」「テストの網羅性」を把握できるようにするため。
  - 「何ができるようになったか」はフラットな箇条書きにせず、`■機能名 → その機能でできること（複数可）`の形でグルーピングする。
    例：
    ```
    ■ クリック計測機能
    　→ アクセスを日時・端末・ブラウザ単位で記録できる
    　→ 記録に失敗しても転送は影響を受けない
    ```
  - テスト結果のGWTも、1つの大きな表にまとめず、`■◯◯機能のテスト`という見出しごとに機能単位の小さな表に分割する。
